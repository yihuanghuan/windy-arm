### 1.1 位置模式在 joint2 上有约 10° 的不可消除误差

曾试图用位置模式把 j3 从 −1.3579 复位到 −1.0927：j3 修好了（偏差 15.19° → 2.67°），
但 **j2 从 0.31° 恶化到 10.19°**，且在 t=3s 就卡死、之后 70 秒纹丝不动（5.57° → 5.55°）。

这是**静摩擦停滞**：j2 静摩擦 **1.775 Nm，是其余关节的 2.4~18 倍**，死区 0.0592 rad，
同时它承载最重（重力约 3 Nm）。位置误差乘 kp 顶不过静摩擦。

**不要再用位置模式硬顶 j2。** 正确做法是接受实物当前位形 —— 把只读工具读到的六个值
写进 `initial_pose_rad`，再重跑 3.2 的可达性/安全校验。`_solve_initial_pose` 会用多起点
解出轨迹起点并选限位余量最大的分支，approach 段负责平滑过渡过去。

`0x12`/`0x22` 的单位是 **Nm 不是安培**（量化步长反解，四条全落在干净整数上）。

### 6.2 为什么必须加笔架

末端取 link6 原点时它落在腕转轴上，**q6 转动不移动末端**，只贡献 5D 任务的 2 行姿态行，
近奇异时掉秩。取笔尖 link7（外移 91 mm）后 q6 有力臂，位置行也贡献。

沿轨迹 100 点实测：**6D 姿态可达 43% → 100%**，5D 的 σ最差 0.0082 → 0.0194。
闭环 RMS 10.35 → 3.95 mm。**写字本来就要装笔，这个工具无论如何都要有。**

### 6.3 为什么 6 关节用水平书写面而 7 关节用竖直板

竖直板要求腕部产生**水平**笔轴，而 6 关节**没有球腕**（joint5 绕 z、joint6 绕 x）。
7 关节多一个自由度不受此限。实测（站心附近 20 点）：

```
6 关节  竖直板 限位余量 0.126 σ 0.0075  |  水平面 限位余量 0.47~0.52 σ 0.081~0.143
7 关节  竖直板 达标            |  水平面 RMS 353.9mm 峰值 587mm 96.4% 力矩饱和
```

**同一几何对两种腕部结构好坏相反**，所以做成了可选（见 7.5）。

### 6.4 `whole` 任务曾经卡在 2.42 mm 的根因（四路诊断 + 对抗核验）

> ⚠️ **这一节描述的是笔轴修正【之前】的状态**。修正后 RMS 已降到 0.061 mm，
> 下面的根因链不再是当前瓶颈。保留它是因为**已定量排除的方向**（本节末尾）
> 仍然成立，可以避免重复劳动。

误差 >1mm 的时间只占 **2.68%**，却贡献绝大部分 RMS；**非事件时段误差中位 0.0196 mm**。

根因链（每一环都有真实 ROS 数据）：

```
基座摆动在末端引起 0.156 m/s（是画笔速度 0.064 m/s 的 2.4 倍）
   ↓ 抵消它的关节速度代价【强烈依赖位形】：同一 5D 位姿，好位形只要 11~24% 速度包线，
     控制器所在位形要 103~694%（差 6~40 倍）
   ↓ 撞上 torque_sim_arm.cc:306 的速度硬夹 [3,3,3,5,5,5] rad/s
     —— 控制器全链路【没有任何一处建模它】
   ↓ plant 逐轴夹 → 末端加速度【方向】被转掉（不是沿路径滞后）
   ↓ 误差起飞 → SMC(λ=72,k=102) 索要 −727.50 Nm（40 倍限幅）→ 六轴饱和 → 41 mm
```

**已定量排除**（都做了真实 ROS 反事实，不要重做）：

* 放松 `max_velocity`：×1.5 无改善、×3 峰值翻倍、×30 发散到 50 mm、×0.5 变 11 mm。
  **且 ×3 时安静时段误差地板从 0.0196 塌到 0.188 mm（10 倍）** —— 那个地板是 1 mm 目标所依赖的。
* 放松力矩上限：`tau_scale=2` 时 RMS 反而 2.018 → 4.949，速度夹翻倍。
* TOPP 时间参数化：尖峰时段所需末端速度 **约 100% 来自基座补偿**，重新分配时间削不掉。
  画笔放慢 5 倍，包线占用率只从 1.051 变到 1.067。
* 分段边界不连续：参考轨迹在全部 86 个内部边界上**可证 C2 连续**
  （`_smoothstep` 是五次多项式，`_interpolate_rotation` 套同一个 smoothstep）。
* 零空间参数：6 次真实 ROS 改 `q_nominal`/`kp`/`kd` 全部无效或更差，理论上限只值 0.5~2%。

**理论上限**：剔除硬夹样本后 RMS = 0.047~0.47 mm。所以修好它就能到 1 mm 以下。

## 7. ⚠️ 陷阱（每一条都真实发生过）

### 7.1 笔轴是末端 **x** 轴（RViz 红轴）

依据是**物理笔架的安装方向** —— 笔沿 `link7` 的 x 轴延伸。

取错的后果不是精度下降，而是**约束方向反了**：放开该锁死的笔尖指向、锁死无所谓的绕笔自转。
而且 `pen_axis_error()` 用的是同一个轴，**自己验自己不会报警**。

实测把它从 y 改成 x：`hwtest` RMS 0.0256 → **0.0041 mm**，
`whole` RMS 2.42 → **0.061 mm（40 倍）**、峰值 1.13 mm，**顺带达标**。

⚠️ 这意味着第 6.4 节那条根因链（基座补偿速度代价 → 撞速度硬夹 → 力矩饱和 → 41mm 尖峰）
**上游其实是笔轴约定错了**。那些诊断数据本身没错，但测的是错误任务定义下的现象。

约定分两套，由 `MB_STATION_LAYOUT` 决定，`_station_geometry` 的 `top` 站两种共用所以也随之切换：
`vertical`（7 关节历史基线）用 y 轴，`horizontal`（6 关节实机）用 x 轴。

回归测试 `test/test_pen_axis_convention.py` 用笔画点云的 SVD 法向做独立基准，
并额外核对**两份 6 关节配置一致**、**代码默认值与配置一致**。


### 7.2 `first_moment_ratio` 已烘进 URDF，**不可再乘一次**

`config/arm6.urdf` 和 `arm6_tool.urdf` 的 link1~6 惯性参数**已按实机标定修正**
（质量标度 `[1.005, 1.336, 1.418, 1.220, 1.0, 1.361]`）。模型算出的重力**就是**实机重力。

再乘一次是重复修正 —— 曾在 `test_phase2_probe.py` 里出现，把 2.83 Nm 夸大成 4.09 Nm。

**改了连杆惯量必须同步重算 armature**，使 `M_连杆 + armature = 实测总惯量`（回代校验精确相等）。
`config/arm.urdf`（7 关节）**未修正**，仍是 CAD 名义值，对它该系数仍然适用。

### 7.3 `install/` 里的 Python 是**副本不是符号链接**

`install(DIRECTORY task_space_smc/ ...)` 装的是副本。改了 `.py` 或 `.yaml` **不重新
`colcon build` 就不生效**，节点跑的是旧代码。验证：

```bash
diff src/arm-platform/task_space_smc/core/redundancy_resolution.py \
     install/manipulator/lib/manipulator/task_space_smc/core/redundancy_resolution.py
```

### 7.4 `/joint_states` 可能有第二个发布者

复位监控时 `/joint_states` **间歇出现完全不同的位姿**（相差 74°），3 秒后又恢复。机械臂
不可能这样运动。本次会话早先也出现过同类问题（多个 `student_arm_node` 实例导致 371 mm 误差）。

**读实物真值只信 `pose_check_readonly.py`**（直接读串口，绕过 ROS）。
任何物理上不可能的跳变，先查数据源，不要查动力学。

### 7.5 `demo/moving_base_trajectory_config.py` 是**共享文件**

被 7 关节 SMC 通路、`pinocchio_ik`、MPC demo、visualizer、
`demo/test_moving_base_trajectory_shapes.py` 共同 import。

工作面朝向由 `MB_STATION_LAYOUT` 控制，**默认 `vertical`（原竖直板），不要改默认值**。
`horizontal` 由 6 关节 launch 用 `os.environ.setdefault` 显式声明。曾把默认改成
horizontal，直接让 7 关节从达标发散到 RMS 353.9 mm。

**7 关节基线需要重新存档**：它此前"已验证达标"的数字是在改 `torque_sim_arm.cc` 限幅逻辑
（额定→峰值）和 armature 跳过逻辑**之前**测的，现在数字未知。README 第 13 节的能力边界表
需要相应更新。另外它的配置仍写着 500 Hz，而实机固件只有 200 Hz。

### 7.6 单元测试全绿 ≠ 闭环稳定

实施"饱和感知解算"（SNS，逐轴钉住+其余关节重解）时：

```
161 个单元测试全绿
真实 ROS 8 次重复：RMS 245.7 mm（对照不用它是 2.43 mm）—— 坏 100 倍
```

单元测试只验**孤立时刻**的盒约束是否满足，验不出闭环稳定性。代码保留在
`redundancy_resolution.py`（`FeasibilityLimits` / `_saturation_aware_task` /
`_feasible_acceleration_box`），但 runner 里已 **`feasibility=None` 停用**。

**要重新启用必须先在真实 ROS 上验证。** 第 5 节那条规则就是这么来的。

### 7.7 已修的一个 bug：零空间投影不是投影

`N = I − J̄·J` 里的 `J̄` 原本是**阻尼**逆，不是伪逆，所以 `N² ≠ N`，零空间运动**漏进任务
空间**。实测泄漏在近奇异时从 3.5e-09 涨到 2.4e-03（6 个数量级），触发正反馈：
`σ 下滑 → 阻尼升 → 泄漏涨 → 当作任务扰动 → 六轴饱和 → 41 mm`。

已改为截断伪逆 `_undamped_inverse()` 专供投影，任务项仍用阻尼逆（奇异保护不变）。
效果：泄漏 3.7e-02 → **3.3e-14**，8 次重复变异系数 48.5% → 18.5%，偶发大跳变消失。
回归测试 `test/test_nullspace_projector_is_exact.py`（13 条，**已验证旧实现下 10 条会失败**）。

⚠️ **当前仿真里的基座摆动幅值是自拟的**（`BASE_CIRCLE_RADIUS=0.01`、
`BASE_Z_AMPLITUDE=0.01`，末端处 0.156 m/s）。实机基座固定在桌边，阶段 A 根本没有这个扰动
（launch 里已设 `MB_BASE_RADIUS=0`）。阶段 B 的扰动幅值/频率**应当用动捕实测**，
不要继续用自拟值 —— 否则会重复"花大力气对付一个不存在的工况"。

**方法学要点**（详见 `PHASE1_FINDINGS.md`）：

* 斜率法免疫摩擦：`d(Δq)/d(t_ff) = α/kp`、`d(qdd)/d(τ) = 1/M`，摩擦只进截距。

  节点模式不对（跟踪误差=命令、tau≈0）。

## 10. 实机上机记录（2026-08-02 夜）

四次力矩模式上机，**全部中止**，但每次都定位到一个基础设施缺陷。控制律本身尚未得到检验。

| 次 | 结果 | 定位到的缺陷 |
|---|---|---|
| 1 | 节点启动即中止 | `ros2 run` 缺 `motor_config_path`，`AL1::Init` 抛异常。**未发出任何字节** |
| 2 | 机械臂乱动、操作者断电 | approach 段在硬件模式下**不驱动机械臂** |
| 3 | 同上 | ROS **域冲突**（见 10.2） |
| 4 | **看门狗按设计触发**，机械臂被按住 | **满幅力矩零响应**，见 10.3 |

### 10.1 已修复的三处代码缺陷

**① approach 段在硬件模式下不驱动机械臂**（`whole_task_smc_ros_runner.py`）

```python
if self.simulated_base:
    self._run_approach(elapsed, now)      # 只有仿真驱动
elif ...:
    self._publish_start_hold()             # 硬件只发 RViz 可视化
```

那 30 秒里一条力矩指令都没发，电机靠 node 的 hold 锁存撑着；`start_delay` 一到跟踪直接使能，
末端距参考起点 144 mm，SMC(λ=72,k=102) 立刻全力冲。
**实测：使能起点 t=0、关节速度峰值 28.17 rad/s（上限 3/5）、力矩饱和 100%、j4 冲到 233°。**

**② `_solve_initial_pose` 用 6D 姿态误差，与 5D 任务口径不一致**

多约束了绕笔轴的自转，把解逼到劣质分支：实测要求 joint6 转 **229°**、approach 路径上限位
余量降到 **0.000**。改成 5D 笔轴误差 + 多起点按余量选分支后，余量 1.154 rad、位移 91.1°。

**③ 新增运行时安全看门狗**

速度超包线 1.2 倍、或位置误差 >50 mm，立即停止跟踪并**保持位置**
（发位置环默认增益，**不发零力矩** —— MIT 模式下那是彻底失力）。

第 4 次上机时它在 `t=30.06` 触发（joint5 速度 6.31 rad/s），0.06 秒内按住机械臂，
触发后速度峰值降到 0.159 rad/s。**这个看门狗本该在第一次上机前就有。**

### 10.2 ⚠️ ROS 域冲突（最隐蔽的一个）

默认 `ROS_DOMAIN_ID=0` 上**跑着另一套完全独立的系统**：

```
/joint_states 发布者 2 个（都叫 student_arm_node，GID 不同）
节点列表还有: /student_arm_node ×2, /robot_state_publisher ×5, /rviz2,
             /mavros/*, /gsi_search_node, /gsi_mavros_offboard_controller, ...
```

控制器读到的是**两台机械臂交替的状态**。数据特征：相差 46° 的两组位姿在 5 ms 内交替、
`dt` 在 0.0015~0.0029 乱跳（两个 200 Hz 源叠加成 400~600 Hz）、78.4% 的帧与上一帧相同。
日志里的 `Rejected command: expected 6 joint positions, got 7` 也是它。

**上机必须用专属域**（实测域 77 干净）：

```bash
export ROS_DOMAIN_ID=77
# 启动后必须确认：
ros2 topic info /joint_states | grep "Publisher count"   # 必须是 1
ros2 topic hz /joint_states                               # 必须约 200
```

隔离后：发布者 1 个、频率 199.985 Hz、`dt` 恢复 0.005。

> 教训：仿真调参时一直用独立域（41~48、60~91）做隔离，**上实物时却用了默认的 0** ——
> 最需要隔离的时候没隔离。

### 10.3 ⚠️ 部分解决：满幅力矩推 24 秒，机械臂纹丝不动

**2026-08-03 更新：下行通路已用 `serial_tap.py` 独立验证，C++ 侧全部排除。
剩余嫌疑收敛到电机固件对 `kp=kd=0` 的处理，见本节末尾的「已验证」与「下一步」。**

第 4 次上机的 approach 段（t<30，30 秒走 91°，峰值速度只需 0.10 rad/s）实测：

```
j3  恒 −9.00 Nm   标准差 0.00   符号翻转 0 次 / 4682 帧
j4  恒 −1.60 Nm   标准差 0.00
j1  均值 +8.53 Nm
六轴力矩饱和占比 76~99.9%
而 q_j2 精确停在 33.124°，24 秒不变
```

**恒定满幅直流力矩、零响应。** 这排除了控制律不稳（符号不翻转就不是振荡）、
排除了通信丢帧、排除了振荡抵消 —— **力矩没有到达电机**。

#### 已排除的候选（都有实测依据，不要重做）

| 候选 | 排除依据 |
|---|---|
| 固件/串口丢帧 | 只读抓包 5 秒：**201.0 Hz、4140 帧、校验错 0**，六个数据流齐全 |
| 反馈"停更 45.7%" | **这是误判**。机械臂静止时读数本就不变，j1/j2/j3 变化率 0% 正是静止的正确表现 |
| `rate_torque_ = 0` 静默归零 | `src/robotics/arm/a_l1.cc:40` 确实调了 `SetRateTorque(rated_torque)` |
| 近限位时 `kp=0` 被驱动层覆盖 | `dm_motor.cc:63` 的分支要求距限位 <0.05 rad；实测各关节余量 ≥1.02 rad |
| 控制律振荡 | 符号翻转 0%，是恒定直流 |
| ROS 域冲突 | 已隔离到域 77，发布者 1 个、199.985 Hz（见 10.2） |

#### ✅ 已验证：下行通路本身是好的（2026-08-03，`serial_tap.py`）

命令链是
`SMC → MotorControl → DMMotor::UpdateCommand → protocol_->SetCurrent → bus_->Send()`。

**下行方向此前从未被独立验证过** —— 而且**用被动读法原理上就验不了**：UART 不会把
TX 回环到 RX，打开同一个 `/dev/ttyUSB0` 去 `read()` 只能看到上行流；何况串口被控制
节点独占。所以新工具走**伪终端透明中继**：节点开一个 PTY，工具原样转发到真串口，
两个方向同时落盘解码。它还带一个 `--fake-board` 模式，**不碰实物、不用通电**就能
让真正的 `student_arm_node` 接上来验证驱动层。

用 `--fake-board` + 真实 `student_arm_node`（`arm_type:=a_l1`，走完整 C++ 驱动栈）
实测 9.84 s：

```
0x10 position   1969 帧  200.1 Hz     校验错 0   短写 0   截断 0
0x12 torque     1969 帧  200.1 Hz     峰值 |τ| = [8.53, 9.00, 9.00, 1.60, 0.50, 0.25]
                                       ↑ 与下发值【逐位相符】
```

j4~j6 在线上符号取反，正是 `motor_config.yaml` 里 RS05 的 `coord_system: left_hand`
在 `DMMotor::SetCurrent` 中生效；j1~j3 是 `right_hand`，不取反。数值与符号全部自洽。

**因此以下全部排除**（都有实测，不要重做）：

| 曾经的嫌疑 | 排除依据 |
|---|---|
| `ProtocolV1::Pop` 漏发 0x12 | 0x12 与 0x10 帧数完全相等，均 200.1 Hz |
| `DMMotor::UpdateCommand` 早退 | 力矩值逐位正确送达 |
| `SerialBus::SendCore` 丢 `write()` 返回值导致短写截断 | 短写 0 次、残留 0 字节、校验错 0 |
| C++ serial 库开不了 PTY | 节点正常初始化并稳定跑满 200 Hz |

#### ⚠️ 新发现的陷阱：`enable=0` 会被**静默**降级成位置保持

`student_arm_node.cc` 的 `StudentEffortCommandCallback`：`msg->enable == 0` 时
**直接把力矩指令换成带默认增益的位置保持并 return**，**一行日志都不打**；
`ValidateEffortCommand` 在 `enable == 0` 时提前 `return true`，连长度检查都跳过。

而上游 `hardware_enabled` 在**两处默认都是 false**：
`whole_task_smc_ros_runner.py:80` 的 `declare_parameter("hardware_enabled", False)`，
以及 `launch/task_space_smc_whole6.launch.py` 的 `default_value='false'`。
不显式传 `hardware_enabled:=true`，`ActuatorAdapter` 就返回 `enabled=False`
（`actuator_adapter.py:155`），runner 随之发 `msg.enable = 0`。

A/B 实测（其余参数完全相同）：

```
enable=0   0x12 力矩 [0,0,0,0,0,0]        0x13 kp [30,30,30,5,5,5]  ← 默认增益
enable=1   0x12 力矩峰值与下发值逐位相符    0x13 kp 0
```

这个失败模式的表象与 10.3 高度相似：**控制器日志里满幅力矩**（`motor.command`
无论 `enabled` 与否都照算照记），**线上一个字节的力矩都没有**，机械臂被位置环
按在原地不动。

> ⚠️ **但这【不能】断定就是第 4 次上机的原因。** 留存的 8-02 夜间 CSV 里 `enabled`
> 全是 1，且它们末端误差均为 0.0 mm（是仿真记录）；**第 4 次上机的原始数据没有找到**，
> 无法回溯当时的取值。写在这里是因为它是这条路径上一颗真实的地雷，
> 且 `serial_tap.py` 现在会自动认出它（判据：力矩恒 0 而 kp 恒非 0 —— 纯力矩模式
> 的定义就是 `kp=kd=0`，出现默认增益即说明指令被降级）。

#### 下一步：只剩固件这一段

C++ 侧已排除，`0x12/0x13/0x14` 下行帧内容确认正确。所以：

* **帧内容正确而电机不动 → 问题在电机固件对 `kp=kd=0` 的处理。**
  阶段 2 验的是 `0x12` 的【标度】，用的是**位置模式叠加前馈**（kp≠0）；
  SMC 发的 `p=0, d=0, current=τ` 纯力矩组合，实机上从没跑过。

上机时按顺序做两件事，一次上机名额就够：

1. 起 `serial_tap.py` 做中继（真串口模式），确认下行 0x12 正确**且**上行 0x22
   是否跟随。工具会直接给结论 —— 0x22 不跟随即锁定固件。
2. 旁证实验：把 SMC 的 `msg.p` 从 0 改成小值（如 5.0），若机械臂开始响应，
   即确认纯力矩模式（kp=0）在这台固件上不工作。

### 10.4 上机检查清单

1. `export ROS_DOMAIN_ID=77`（非 0）
2. `pose_check_readonly.py` 读实物位形 → 写进 `initial_pose_rad`
3. 重跑可达性/安全校验（第 3.2 节判据）
4. 启动硬件节点后确认 `Publisher count: 1` 且 `topic hz` ≈ 200
   —— 注意 `ros2 topic list/info` 会读 **daemon 缓存**，实测出现过节点已在、话题却
   列不出来的情况。查话题一律加 `--no-daemon`，否则会误判成"订阅没建起来"。
5. **确认 `hardware_enabled:=true`**，否则力矩指令会被静默降级成位置保持（见 10.3）
6. `start_delay_sec` 给足（30 s 起），确认日志打出"初始位形: 限位余量 …，需移动 …°"
7. 全程手放断电开关 —— 协议无急停通道
