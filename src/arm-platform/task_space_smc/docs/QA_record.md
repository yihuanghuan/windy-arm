# Vicon 接入：投递抖动被当成了基座运动

日期：2026-08-04
适用：`hw/vicon_floating_base_bridge.py`、`launch/vicon_floating_base.launch.py`、
`config/smc_params_hold.yaml`

一句话：**桥用"包什么时候到"当作"帧什么时候拍的"，把 WiFi 的投递抖动直接微分成了
基座速度和加速度。** 数据本身几乎是完美的，噪声是我们自己造的。

---

## 1. 症状

接上动捕跑保持 demo 前的验收测试里看到两件事：

1. 桥不停刷 `Vicon sample gap 0.103s; reset derivative estimates` —— 90 秒里 262 次。
2. 基座**静止不动**时，`/floating_base/vicon` 里的导出量却很大：

   | 量 | 静止时的 std |
   |---|---|
   | 线速度 | 4.5 / 2.7 / 5.0 mm/s |
   | 角速度 | 0.095 / 0.115 / 0.041 rad/s（合成模最大 0.69 rad/s ≈ 40°/s） |
   | 角加速度 | 1.80 / 2.16 / 0.79 rad/s²（p95 6.2，最大 16.0） |

角加速度直接进 `compute_task_bias_acceleration` 的偏置加速度、直接变成关节力矩。
16 rad/s² 的伪加速度在 0.3 m 力臂上是 4.8 m/s² 的伪末端加速度需求。

第一轮我把这些归因于"2.4 GHz 校园 WiFi + 动捕噪声"，并据此建议加 USB 网卡走有线。
**那个归因是错的。**

## 2. 名词

| 词 | 含义 |
|---|---|
| **VRPN** | Virtual-Reality Peripheral Network，动捕/追踪设备的开源网络协议。Vicon Tracker 内置 VRPN 服务器，默认端口 3883 |
| **`msg_time`** | VRPN 回调结构 `vrpn_TRACKERCB` 里的时间戳字段，由**服务器**在生成消息时填写。对 Vicon 来说就是那一帧的采集时刻 |
| **源时钟 / 采集时刻** | Vicon 服务器自己的时钟。与本机不同步 |
| **到达时刻** | 本机收到这条 ROS 消息的时刻 |
| **传输延迟** | 到达时刻 − 采集时刻（扣掉常量钟差之后） |
| **dt** | 相邻两帧之间的时间差，微分求速度时的分母 |
| **陈旧性判据 (staleness)** | 运行器的安全检查：手里的基座状态超过 `base_state_timeout_sec` 就停发力矩 |

## 3. 根因

### 3.1 真时间戳一直都在，只是被丢掉了

`vicon_perception_ws/src/vrpn_listener/src/vrpn_listener.cpp:35-36`：

```cpp
pose_msg.header.stamp.sec     = poseData.msg_time.tv_sec;
pose_msg.header.stamp.nanosec = poseData.msg_time.tv_usec * 1000;
```

**header 里放的是 Vicon 服务器的帧时间戳**，不是到达时刻。而桥（改动前）在
`_pose_cb` 里做的是：

```python
now = self.get_clock().now().nanoseconds * 1e-9   # 本地到达时刻
...
dt = now - self.prev_t                             # 用到达间隔当 dt
raw_v = (p - self.prev_p) / dt                     # 微分
```

### 3.2 到达间隔是坏的，源时钟间隔是好的

30 秒 / 3601 条实测（2.4G、−61 dBm、power_save off）：

| dt 来源 | 中位 | p05 | p95 | 最大 | std | 落在众数 ±20% |
|---|---|---|---|---|---|---|
| **Vicon 源时钟** | 8.017 ms | 7.963 | 9.021 | 9.536 | **0.474 ms** | **100.00%** |
| 本地到达 | 6.031 ms | 0.097 | 19.162 | 180.4 | 14.975 ms | **14.67%** |

- Vicon 原生帧率 **123.5 Hz**（帧间隔众数 8.10 ms）
- **真实丢帧只有 2.81%**（104 / 3705）。数据几乎没丢，只是到得不齐

WiFi 把 UDP 包压成串投递：**最小到达间隔 0.087 ms**。真实位移 8 ms 除以 0.087 ms 的
假 dt，速度就放大 **92 倍**。这就是全部噪声的来源。

### 3.3 同一批位移，只换 dt（**原始差分**，未经滤波）

| dt 来源 | 线速度 std (mm/s) | 线速度峰值 | 角速度 p95 | 角速度峰值 |
|---|---|---|---|---|
| 本地到达 | 40.6 / 22.3 / 44.9 | 1.008 m/s | 3.84 rad/s | **28.2 rad/s** |
| **Vicon 源时钟** | **1.3 / 0.8 / 1.8** | **0.017 m/s** | **0.178 rad/s** | **0.427 rad/s** |

原始差分层面：线速度噪声降 **30×**、峰值降 **59×**；角速度 p95 降 **22×**、峰值降 **66×**。

> ⚠️ **这个倍数不会原样传到桥的输出上。** 桥有一个 40 ms 一阶低通
> （`filter_time_constant_sec`），它把大部分吸收掉了。真正的对照见
> [4.4](#44-实测对照ab同一条流同时喂两个桥)——**输出端的改善是 1.5~2.5 倍，不是 30 倍。**
>
> 但旧实现里那个滤波器本身也吃坏 dt：系数 `alpha = dt / (tau + dt)` 在突发时
> （dt=0.09 ms）掉到 0.002 几乎冻结，在空档时（dt=180 ms）升到 0.82 几乎不滤。
> **它不是在按 40 ms 时间常数滤波，而是在被网络抖动调制**，等效带宽和滞后都不可控。
> 换成源时钟 dt 之后 `alpha = 8/(40+8) = 0.167` 恒定，滤波器才真的是 40 ms 低通。

### 3.4 钟差是时区，不是随机

最小差法定标出来的偏置：**−43204.607 s = −12.0013 小时**。
12 小时是时区差，剩下 4.6 秒才是真实钟差。ETH-ASL 的 `ros_vrpn_client` 里有同款处理
（把 tracker 与系统时钟的差按整小时取整，注释写明是 "timezone difference in the
tracker software"）。**所以源时间戳不是垃圾数据，可以放心用它的差。**

## 4. 解决方案

把时间戳的两个职责拆开：

| 职责 | 用哪个时钟 | 为什么 |
|---|---|---|
| **算 dt 做微分** | Vicon 源时钟的差 | 它是数据真实的采样节拍，与网络无关 |
| **发布的 header.stamp** | 本地时钟 | 运行器的陈旧性判据要和自己的 `now` 比 |

关键在于发布的 stamp 应该是**采集时刻映射到本地时钟**，而不是**到达时刻**：

```
stamp_local = 源时间戳 + 钟差偏置
钟差偏置    = 滑动窗口内 min(到达时刻 − 源时间戳)
```

用**最小值**而不是均值：窗口内延迟最低的那条消息最接近"零延迟"，它才反映纯钟差。
用**滑动双窗口**而不是一次定标：既 O(1)，又能跟随时钟漂移，不会被某条走运的早期
包锁死。这套做法与 `byu-magicc/optitrack_vrpn` 的混合打戳法同源（他们取前 N=100 条
的最小差作常量偏置）。

**为什么这更安全**：到达打戳会把一条在空中飞了 180 ms 的样本报成"0 ms 新鲜"，
陈旧性判据完全失效；采集打戳报成"180 ms 旧"，判据才做了它该做的事。

### 4.1 实际改了什么

| 文件 | 改动 |
|---|---|
| `hw/vicon_floating_base_bridge.py` | 新增 `_source_time()` / `_clock_offset()`；`dt` 改用源时钟；`header.stamp` 改为采集时刻；`max_sample_gap_sec` 判据随之作用在源时钟上 |
| 同上 | 订阅队列深度 `10` → 参数 `input_queue_depth`（默认 **200**） |
| 同上 | 新增周期性统计日志（速率 / 传输延迟 / 丢帧数），供上机前验收；首窗口标注为预热 |
| `core/base_state.py` | `RosFeedbackBaseState.update()` 拒绝比手里更旧的样本 |
| `config/smc_params_hold.yaml` | `base_state_timeout_sec` `0.1` → **`0.15`** |
| `test/hw/test_vicon_bridge_timestamps.py` | 新增 12 条回归测试 |

`update()` 那条乱序保护是配合深队列的：排空积压时会连发一串**真实很旧**的帧，
顺序正常时最后一条最新，但一旦乱序，无条件覆盖就会用旧位姿顶掉新位姿 ——
而陈旧性判据**看不出来**，因为那个旧时间戳本身是诚实的。

新增参数：

| 参数 | 默认 | 说明 |
|---|---|---|
| `use_source_timestamp` | `true` | 关掉即回到旧行为（到达打戳），用于对照 |
| `clock_offset_window_sec` | `5.0` | 钟差估计的滑动窗口。有效窗口是 5~10 s |
| `input_queue_depth` | `200` | 订阅队列深度 |
| `stats_interval_sec` | `10.0` | 统计日志周期，`0` 关闭 |

### 4.2 队列深度为什么必须加大

WiFi 一次突发能投递几十帧（最小间隔 0.087 ms）。深度 10 的队列在节点**内部**丢包，
丢的是网络已经送到的数据：实测 2.4G 丢 **4.5%**、5G 丢 **14%**。这与网络质量无关，
纯粹是配置太浅。

### 4.3 `base_state_timeout_sec` 为什么从 0.1 提到 0.15

改用采集打戳后，运行器比的是**真实年龄**（含传输延迟），数值天然变大。
按 200 Hz 控制环回放 5999 拍：

| 阈值 | 超阈（停发力矩）的拍占比 |
|---|---|
| 0.05 s | 11.64% |
| **0.10 s（旧值）** | **3.47%** |
| **0.15 s（新值）** | **0.42%** |
| 0.20 s | 0.00% |

⚠️ **不要为了跑通再往上调。** 190 ms 前的基座位姿拿去算补偿本身就是错的；
停发力矩、由驱动的指令超时接管保位，是设计好的正确行为。

### 4.4 实测对照（A/B，同一条流同时喂两个桥）

前后分开测会被 WiFi 干扰随时间变化污染（"这 30 秒比上 30 秒安静"）。所以起两个桥
订阅**同一个** `/vrpn/arm_base/pose`，只差 `use_source_timestamp`，同时采样 30 s。
基座静止，两个桥都跑过预热窗口：

| 量（基座静止） | 源时钟打戳（新） | 到达打戳（旧） | 改善 |
|---|---|---|---|
| 线速度 std (mm/s) | 0.3 / 0.0 / 0.2 | 0.4 / 0.0 / 0.2 | — |
| 线速度 峰值 (m/s) | **0.0019** | 0.0029 | 1.5× |
| 角速度 峰值 (rad/s) | **0.1028** | 0.1507 | 1.5× |
| 线加速度 峰值 (m/s²) | **0.0382** | 0.0709 | 1.9× |
| 角加速度 std_y (rad/s²) | **0.262** | 0.440 | 1.7× |
| 角加速度 p95 (rad/s²) | **0.692** | 1.041 | 1.5× |
| **角加速度 峰值 (rad/s²)** | **1.519** | **3.746** | **2.5×** |

**峰值改善最明显**，这正是最要紧的一项：偏置加速度的尖峰直接变成力矩尖峰。

安全性的改善比噪声更大：

| | 源时钟打戳（新） | 到达打戳（旧） |
|---|---|---|
| 上报样本年龄 中位 | 3.5 ms | 0.9 ms |
| 上报样本年龄 p95 | **96.8 ms** | 4.3 ms |
| 上报样本年龄 最大 | **190.8 ms** | 21.3 ms |

新值与独立探针实测的真实年龄（p95 84 ms、最大 190 ms）吻合。
**旧实现把最旧到 190 ms 的样本报成不超过 21 ms —— 陈旧性判据基本失效。**

> 起节点后的**第一个统计窗口是预热**，不能当验收依据：DDS 发现 + Python 预热会卡住
> 约 1 s，200 深的队列（≈1.67 s）如实缓存那一段，于是这批帧的年龄天然很大
> （实测首窗口 max 1046.9 ms，次窗口即回到 193 ms）。它们**确实**很旧，
> 运行器按年龄丢掉就对了。日志会给这一窗口打上 `(预热窗口，不作验收依据)`。

## 5. 还没解决的（改代码修不掉）

**传输延迟的长尾。** 同一批数据的相对传输延迟：

| 中位 | p95 | p99 | 最大 |
|---|---|---|---|
| 3.77 ms | 79.9 ms | 125.8 ms | 185.6 ms |

`>20 ms` 占 19.5%，`>50 ms` 占 10.6%，`>100 ms` 占 3.17%。

这是 802.11 MAC 层重传的物理事实（数据走的是 UDP，`ss` 已确认，不是 TCP 队头阻塞）。
空档的时间分布是**成簇**的：安静时能连续 10 秒零空档，干扰来时每 0.2 s 一次。
2.4 GHz 信道 2437 上有 6 个 AP，算上重叠信道共 15 个在争用。

**唯一的真解是有线**（本机没有以太网口，需要 USB 网卡或扩展坞）。
但**它不再是上机的前置条件**：改完上面几条之后，WiFi 下的数据质量已经够跑保持 demo。

### 5.1 桥进程被抢 CPU（操作陷阱，不是缺陷）

深队列（200 帧 ≈ 1.67 s）会把**桥进程的 CPU 饥饿**转成一串很旧的帧。实测：在同一台机
上跑整套 pytest（588 条）期间，桥报出 `mean 572.6 ms, max 2208.3 ms`；测试一结束
立刻回到 `mean 8~21 ms, max 127~189 ms`。

这不是缺陷 —— 那些帧**确实**有 2.2 s 那么旧，运行器按年龄丢掉是对的。但它意味着：

- **上机跑 demo 时不要在同一台机上跑重负载**（编译、整套测试、RViz）。
  `vicon_hold_demo.launch.py` 的 `rviz` 默认就是 `false`，别随手打开。
- 桥是单线程 Python 节点。它和 200 Hz 控制环、驱动抢的是同一批核。
- **统计日志能直接看出来**：`transport latency mean` 突然从十几毫秒跳到几百毫秒，
  查的是本机负载，不是网络。

### 5.2 网卡电源管理（已处理）

本机 `/etc/NetworkManager/conf.d/` 里全局 `wifi.powersave = 3`（开），
连接配置是 `default` → 每次重连都会被重新打开。`iw dev wlo1 set power_save off`
只在当前关联内有效，切换网络即失效。

已改为写进连接配置：

```bash
sudo nmcli connection modify "西湖大学-2.4G" 802-11-wireless.powersave 2   # 2 = disable
```

实测收益：p95 到达间隔 22.9 → 20.2 ms，最大 353 → 206 ms。

### 5.3 频段结论

| 配置 | 平均 | p95 | 最大 | >100ms / 20s |
|---|---|---|---|---|
| 2.4G −61 dBm, ps on | 120.0 Hz | 22.4 ms | 260 ms | 5 |
| 5G −69 dBm, ps on | 120.8 Hz | 25.5 ms | 550 ms | 26 |
| **2.4G −61 dBm, ps off** | **120.7 Hz** | **20.2 ms** | **206 ms** | **18** |
| 5G −70 dBm, ps off | 119.8 Hz | 28.8 ms | 377 ms | 29 |

**留在 2.4G。** 本实验室位置的 5G 信号弱 9~10 dB，5745 信道上还挤着 9 个 AP，
两项都抵消掉了 5 GHz 本该有的优势。

## 6. 复现与验收

上机前验收动捕数据时，看桥的周期性统计日志：

```
Vicon 123.4 Hz over 10s | transport latency mean 5.2 ms, max 92.3 ms | source-clock gaps 3
```

- **速率**应接近 Vicon 的原生帧率（本系统 123.5 Hz）
- **transport latency max** 是这一窗口里最旧的样本年龄，它要明显小于
  `base_state_timeout_sec`
- **source-clock gaps** 是**真实丢帧**次数。它现在只在真丢帧时增加；
  如果这个数很大，那才是动捕或网络真的有问题

自查探针（只读，不发布任何话题）保存在会话 scratchpad 里，需要时可以重建：
量到达间隔 vs 源时钟间隔、量传输延迟、按控制环回放模拟陈旧性判据。

## 8. 教训

**任何"传感器噪声很大"的结论，先分清是数据坏了还是时间戳坏了。**
判据很简单：把同一批数据换一个 dt 来源重算一遍。这次一换，原始差分就降了
30~66 倍，说明数据从来没坏过。

第一轮在没做这个区分的情况下给出的两个结论都是错的：
"动捕角加速度噪声比仿真假设高 120 倍"、"必须上有线才能跑"。

**第二个教训：改善要在输出端量，不要拿中间量的倍数当结论。**
原始差分降 30~66 倍，但桥输出端只降 1.5~2.5 倍 —— 因为 40 ms 低通把差额吸收了。
两个数都真，但**能写进结论的是输出端那个**，因为控制器吃的是输出。

**第三个教训：前后分开测会被环境漂移污染。** 这次的 WiFi 干扰是成簇的，
安静 10 秒、风暴 3 秒。同一件事前后测两次能差好几倍。
所以最终对照是**同时**起两个桥订阅同一条流，只改一个参数。
